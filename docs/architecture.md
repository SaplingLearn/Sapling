# Sapling Backend Architecture

The backend ingests student documents, runs Gemini-powered classification, summarization, and assignment/concept extraction, and serves a knowledge-graph-backed tutor and quiz engine to the React frontend.

## High-level shape

A single FastAPI app (`backend/main.py:87`) mounts every router under `/api/<name>`. Supabase is both the datastore and the source of user identity — accessed exclusively through a thin PostgREST wrapper (`backend/db/connection.py:102`) using a service-role key. All LLM work runs as Pydantic AI agents under `backend/agents/` (Gemini via `pydantic-ai-slim[google]`; per-task model slots and the `SAPLING_MODEL_MODE` test seam in `agents/_providers.py`) — the legacy raw-call seam (`services/gemini_service.py`) was deleted in #151 (ADR 0024). The React app in `frontend/` is the only consumer of these endpoints; there is no public/third-party API surface.

## Request paths

- **Document upload** — `backend/routes/documents.py` `upload_document` (streaming SSE; `/upload/sync` is the JSON twin on the same pipeline): validate → `extraction_service.extract_text_from_file` → classifier agent (serial gate) → summary + concept-extraction (+ syllabus when flagged) worker agents in parallel via `asyncio.gather` → `apply_concepts_to_graph` merge → optional `save_assignments_to_db` for syllabi + graph backstop → insert `documents` row (offering-keyed, encrypted summary/concept_notes) → post-roll (invalidate `study_guides` cache, `update_course_context`, `check_achievements("documents_uploaded")`, RAG chunk indexing). Agent failure is terminal: a retry-friendly 502 on `/upload/sync`, an `error:failed` + `status:done` SSE pair on `/upload` (ADR 0024). Idempotent replays key on `X-Request-ID`. `/upload/sync`'s pipeline is a DBOS-durable workflow when the opt-in flag is on (ADR 0011; off by default, no-op decorators), streaming stays intentionally non-durable with X-Request-ID replay as the crash semantic.
- **Chat with tutor** — streamed via `chat_tutor_agent`: `backend/routes/learn.py` builds the run (`_prepare_chat_run` — live graph context + cached `course_context` + retrieval tools per ADR 0023) and `services/chat_stream.py::stream_agent_turn` yields SSE token/graph_update/done events; graph writes ride in-band agent TOOLS and land through `apply_graph_update`, which lazy-imports `update_course_context` for any touched course. The JSON `/chat`, `/start-session`, and `/action` routes run the same agent non-streaming; failures map to 413/502 and the streamed rung ladder is described in ADR 0024.
- **Quiz generation** — `backend/routes/quiz.py` `generate_quiz` loads the target node + prior `quiz_context` and runs the Pydantic AI `quiz_agent` (`backend/agents/quiz.py`, tools pull class-wide misconceptions/weak areas themselves); on agent failure it degrades to HTTP 502 (the raw-Gemini legacy fallback was retired in #145). Result is stored in `quiz_attempts`.
- **Study guide** — `backend/routes/study_guide.py` `_generate_and_insert` fetches the exam row + all offering `documents`, concatenates decrypted `summary` + `concept_notes` into a context block, runs `study_guide_agent`, and inserts into `study_guides` (502 on failure). The `/guide` GET serves cache-first; `upload_document` invalidates by deleting that user+offering's rows.
- **Calendar / syllabus** — covered by the syllabus branch of `upload_document` above (`save_assignments_to_db` deduplicates by trimmed-title + calendar-day). The standalone `backend/services/calendar_service.py:168` `process_and_save_syllabus` exists for direct OCR→Gemini→DB use but is not currently wired to a route.

## LLM seam (current)

Every LLM call is a Pydantic AI agent under `backend/agents/`; there is no other sanctioned LLM seam (the legacy `services/gemini_service.py` raw-call helper was deleted in #151 — ADR 0024). `agents/_providers.py` is the single chokepoint: per-task model slots (`model_for(task)`, overridable via `SAPLING_MODEL_<TASK>` env vars), loop-safe Google providers, and the `SAPLING_MODEL_MODE` seam (ADR 0019) that swaps every agent onto deterministic FunctionModel handlers for tests and the E2E lanes — code below that seam must never construct a raw `google.genai.Client` without a `model_mode()` gate (#439; `services/rag_service.py` holds the one gated embedding client). Usage/cost capture rides `agents/usage.py::record_agent_usage` on every run (#118), and the eval harness (ADR 0021) replays six committed cassette datasets against the agents' real prompts and schemas. When an agent fails, routes degrade honestly — mapped 413/502s, terminal SSE errors, or best-effort empty results — never a second prompt stack (the rung ladder is specified in ADR 0024). Outside that gated embedding client, the only raw `google-genai` caller is `scripts/_raw_gemini.py`, an offline benchmark baseline that never runs in the request path; its docstring forbids importing it from application code.

## Data layer

All Supabase access goes through `backend/db/connection.py:102` `table()`, which returns a `SupabaseTable` wrapping `select/insert/update/upsert/delete` over PostgREST with a single shared `httpx.Client`. There is no ORM. Schema is now delivered as ordered raw-DDL migrations under `backend/db/migrations/` (`0001`–`0028`), applied by a minimal psycopg runner (`backend/db/migrate.py`) over the Supabase *direct* connection string — the one sanctioned exception to the `table()`-only convention, since PostgREST cannot execute DDL. Staging is populated by an idempotent fake dataset in `backend/db/seed_staging.py`. The client uses `SUPABASE_SERVICE_KEY` (service role), so PostgREST runs without RLS enforcement; ownership is enforced in route code by filtering every query on `user_id` and validating via `_validate_user`.

## Data model

The schema is organized into eight bounded domains — Academics, Identity, Gradebook, Knowledge Graph, Study, Analytics, Ops, and Gradescope (migrations `0019`–`0028`). The central change is the catalog/offering/term split: an abstract `courses` catalog, per-term `course_offerings` (FK to `courses` + `terms`), and `terms`; the old `user_courses` table became `enrollments` keyed on `offering_id`. Different domains key on different levels of this split, bridged by `services/academics.py` (`current_term`, `resolve_offering`, `offering_course_id`): the knowledge graph stays on the **abstract `course_id`** so mastery is cumulative across terms, the gradebook keys on **`enrollment_id`**, and study artifacts + class analytics key on **`offering_id`**. The HTTP API boundary still speaks the abstract `course_id`; the resolver translates inward.

Identity is likewise split: `users` is slimmed to account state, with a 1:1 `user_profiles` table holding the encrypted name/profile fields; `services/profiles.py` provides decrypted display-name reads. The gradebook is enrollment-keyed (`gradebook_categories` with drop-lowest, enrollment-keyed `assignments`, plus curve policy on `enrollments`), and class analytics moved to `offering_concept_stats` / `offering_summary` (was `course_concept_stats` / `course_summary`). Knowledge-graph mastery history is now an append-only `node_mastery_events` table (replacing the old `graph_nodes.mastery_events` JSONB column), with UNIQUE-backed upserts for node/edge dedup. Ops tables (`feedback`, `issue_reports`) carry text/uuid PKs and FKs consistent with the rest of the schema.

## Background work

Almost everything currently runs inline on the request path. The one true background task is in `backend/routes/quiz.py:483`, where FastAPI `background_tasks.add_task(_update_context, ...)` defers the post-quiz context regeneration. `backend/services/course_context_service.py:109` `update_course_context` is called inline from `apply_graph_update` and from course add/delete, but its expensive Gemini summary is hash-gated — it only re-runs `_generate_summary_with_gemini` when the stats hash changes. It resolves the touched course to an `offering_id` and upserts into `offering_concept_stats` / `offering_summary`. Achievement checks (`check_achievements`) are also inline and wrapped in best-effort `try/except`.

## Known sharp edges

- `upload_document`'s worker agents run in parallel, but text extraction still runs before the stream opens by default (`OCR_ASYNC_ENABLED` moves it onto a thread inside the SSE context — ADR 0010's lightweight variant), so wall-clock ≈ extraction time + classifier + max(worker) time on the request path.
- `apply_graph_update` (`backend/services/graph_service.py:461`) is called from three routers with different shapes: `backend/routes/documents.py` passes `{"new_nodes": [...]}` only, `backend/routes/learn.py` passes the full `{new_nodes, updated_nodes, new_edges, recommended_next}` parsed out of the tutor's `<graph_update>` tag, and quiz scoring (`backend/routes/quiz.py`, the `submit_quiz` path) now routes its mastery delta through it too — it no longer writes `graph_nodes` directly, instead appending a `node_mastery_events` row via `apply_graph_update`.
- Agent failures no longer degrade to a second pipeline anywhere: a Gemini blip surfaces to the client as a retryable error (502 / terminal SSE / empty scan) rather than being papered over. The one deliberate second chance left is the streamed tutor's Rung-1 non-streaming fast-tier re-run, guarded so it never re-applies landed tool writes (ADR 0024).
- `apply_graph_update` lazy-imports `services.course_context_service` to avoid a circular import; that import path also swallows exceptions so a failing aggregation will not surface to the caller.
- `course_context_service.update_course_context` resolves the course to an offering and writes to `offering_concept_stats` and `offering_summary` synchronously inside the request — a chat turn that touches several courses incurs that aggregation cost serially before returning.
- Document-upload concept population only runs for `category in ("syllabus", "assignment")`; lecture notes, slides, readings, and study guides do NOT auto-populate the graph from upload — that path is the separate `/scan-concepts` endpoints (`backend/routes/documents.py:1106`, `:1149`).
- Sessions are lazy: `start_session` does not persist anything; the row is materialized inside `_consume_pending` on the first `/chat` call, so a session that's started and abandoned leaves no DB trace.
