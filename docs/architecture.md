# Sapling Backend Architecture

The backend ingests student documents, runs Claude-powered classification, summarization, and assignment/concept extraction, and serves a knowledge-graph-backed tutor and quiz engine to the React frontend.

## High-level shape

A single FastAPI app (`backend/main.py:236`) mounts every router under `/api/<name>`. Supabase is both the datastore and the source of user identity — accessed exclusively through a thin PostgREST wrapper (`backend/db/connection.py:400`) using a service-role key. Slow, retryable work can move onto a Postgres job queue drained by a separate `python -m worker` process (`services/jobs.py`, `backend/worker/`; behind the `jobs_queue` flag). All LLM work runs as Pydantic AI agents under `backend/agents/` (Anthropic Claude via `pydantic-ai-slim[anthropic]` since ADR 0030, with any slot able to point back at Gemini; per-task model slots and the `SAPLING_MODEL_MODE` test seam in `agents/_providers.py`). Gemini remains the RAG embedding provider — the legacy raw-call seam (`services/gemini_service.py`) was deleted in #151 (ADR 0024). The React app in `frontend/` is the only consumer of these endpoints; there is no public/third-party API surface.

Routes are the HTTP surface only (#118, #851): no route file is over 600 lines and no function over McCabe complexity 25 (`backend/code_size_baseline.json` is empty; `tests/test_code_size_ratchet.py` keeps it so). Each split route's handler bodies live under the same names in a `services/<domain>/` package (`quiz`, `tutor`, `documents`, `auth`, `social`, `admin`, `profile`, `gradescope`, `flashcards`, `gradebook`), raise that package's domain error, and the route maps it back to the same status and detail. `backend/.importlinter` (`lint-imports`, a CI step) holds the layering `routes | worker` → `services : agents : models` → `db` and lets one domain reach another only through its package `__init__`. The move tables are in `docs/design/domain-modules.md` ("As built (wave 3)"); the routes still re-export every moved name and the old flat module paths are `sys.modules` aliases until the open teammate PRs land.

## Request paths

- **Document upload** — `backend/routes/documents.py` `upload_document` (streaming SSE; `/upload/sync` is the JSON twin on the same pipeline; the bodies live in `services/documents/`: `stream`, `persistence`, `post_roll`): validate → `extraction_service.extract_text_from_file` → `agents/document.py::run_document_agents`, the one agent sequence every upload path runs (classifier agent as a serial gate → summary + concept-extraction (+ syllabus when flagged) worker agents in parallel via `asyncio.gather` → `apply_concepts_to_graph` merge), whose steps `services/document_pipeline.py` turns into the SSE progress events → optional `save_assignments_to_db` for syllabi + graph backstop → insert `documents` row (offering-keyed, encrypted summary/concept_notes) → post-roll (invalidate `study_guides` cache, `update_course_context`, `check_achievements("documents_uploaded")`, RAG chunk indexing). Agent failure is terminal: a retry-friendly 502 on `/upload/sync`, an `error:failed` + `status:done` SSE pair on `/upload` (ADR 0024). Idempotent replays key on `X-Request-ID`. With `jobs_queue` on for the uploader, both routes stage the file in `document_uploads` and a worker runs extraction, the agents, persistence and indexing (`services/document_jobs.py` over the shared `services/staged_jobs.py` state machine); the request relays the worker's stages as the same events, and runs inline if no worker picks the job up within the grace period. `/upload/sync`'s pipeline is a DBOS-durable workflow when the opt-in flag is on (ADR 0011; off by default, no-op decorators), streaming stays intentionally non-durable with X-Request-ID replay as the crash semantic.
- **Chat with tutor** — streamed via `chat_tutor_agent`: `backend/routes/learn.py` is a thin wrapper over `services/tutor/` — `streams.py` serves the two SSE routes, `run.py::_prepare_chat_run` builds the run (live graph context + cached `course_context` + retrieval tools per ADR 0023; the course and message history load concurrently on the async `a*` DB seam), and `services/chat_stream.py::stream_agent_turn` yields SSE token/graph_update/done events (a coroutine `on_complete` runs under `asyncio.shield`, so a client disconnect still persists the turn). Graph writes ride in-band agent TOOLS (`agents/tools/graph.py::apply_graph_update_tool`) and land through `apply_graph_update`, which refreshes the class aggregates of any touched course. The JSON `/chat`, `/start-session`, and `/action` routes (`services/tutor/turns.py`) run the same agent non-streaming; failures map to 413/502 and the streamed rung ladder is described in ADR 0024.
- **Quiz generation** — `backend/routes/quiz.py` `generate_quiz` (body in `services/quiz/generation.py`) loads the target node + prior `quiz_context` and runs the Pydantic AI `quiz_agent` (`backend/agents/quiz.py`, tools pull class-wide misconceptions/weak areas themselves); on agent failure it degrades to HTTP 502 (the raw-Gemini legacy fallback was retired in #145). Result is stored in `quiz_attempts`. Submission (`services/quiz/submission.py`) routes the mastery delta through `apply_graph_update` and defers the aggregate refresh to a `BackgroundTask`.
- **Study guide** — `backend/routes/study_guide.py` `_generate_and_insert` fetches the exam row + all offering `documents`, concatenates decrypted `summary` + `concept_notes` into a context block, runs `study_guide_agent`, and inserts into `study_guides` (502 on failure; an `llm_budget` refusal is a 429). The `/guide` GET serves cache-first under a per-guide single-flight (a cross-replica `app_leases` lease when `stateless_locks` is on); a unique violation on insert replaces that key's row in place, so the code works with or without the `ensure_study_guides_unique_key()` index. `upload_document` invalidates by deleting that user+offering's rows.
- **Calendar / syllabus** — covered by the syllabus branch of `upload_document` above (`save_assignments_to_db` deduplicates by trimmed-title + calendar-day). The standalone `backend/services/calendar_service.py:207` `process_and_save_syllabus` exists for direct OCR→Gemini→DB use but is not currently wired to a route.

## LLM seam (current)

Every LLM call is a Pydantic AI agent under `backend/agents/`; there is no other sanctioned LLM seam (the legacy `services/gemini_service.py` raw-call helper was deleted in #151 — ADR 0024). `agents/_providers.py` is the single chokepoint: per-task model slots (`model_for(task)`, overridable via `SAPLING_MODEL_<TASK>` env vars; the provider is inferred from the model name, ADR 0030), loop-safe Anthropic and Google providers (`_LoopSafeProviderMixin`), the Claude 5.x model profile, and the `SAPLING_MODEL_MODE` seam (ADR 0019) that swaps every agent onto deterministic FunctionModel handlers for tests and the E2E lanes — code below that seam must never construct a raw `google.genai.Client` without a `model_mode()` gate (#439; `services/rag_service.py` holds the one gated embedding client). Every real model carries `_ResilientModelMixin` (`agents/_resilience.py`, #119): bounded retries with jittered backoff, per-slot timeouts, a per-provider circuit breaker and, behind the `llm_fallback` flag, a retry on the other provider; the `llm_budget` flag adds a per-user daily token budget (a friendly 429). Usage/cost capture rides `agents/usage.py::record_agent_usage` on every run, and the eval harness (ADR 0021) replays six committed cassette datasets against the agents' real prompts and schemas. When an agent fails, routes degrade honestly — mapped 413/502s, terminal SSE errors, or best-effort empty results — never a second prompt stack (the rung ladder is specified in ADR 0024). Outside that gated embedding client, the only raw `google-genai` caller is `scripts/_raw_gemini.py`, an offline benchmark baseline that never runs in the request path; its docstring forbids importing it from application code.

## Data layer

All Supabase access goes through `backend/db/connection.py:400` `table()`, which returns a `SupabaseTable` wrapping `select/insert/update/upsert/delete` over PostgREST with a single shared `httpx.Client`. Its async twins on the same handle (`aselect`/`ainsert`/…, `arpc`, `apage_all`; `db/async_connection.py`, #117) serve every `async def` handler: with the `async_db_client` flag off they run the sync verb on the threadpool, on they use a per-event-loop `httpx.AsyncClient`. No `async def` handler calls a sync verb inline (the allowlist in `tests/test_no_sync_db_in_async_handlers.py` is empty). There is no ORM. Schema is delivered as ordered raw-DDL migrations under `backend/db/migrations/` (48 frozen `NNNN_` files, then UTC-timestamp-prefixed ones), applied by a minimal psycopg runner (`backend/db/migrate.py`) over the Supabase session-mode pooler URI — the one sanctioned exception to the `table()`-only convention, since PostgREST cannot execute DDL. Staging is populated by an idempotent fake dataset in `backend/db/seed_staging.py`. RLS is on for every public table and anon/authenticated are revoked (#807); the policies of RLS step 2 exist, but the client still uses `SUPABASE_SERVICE_KEY` (service role), which bypasses them, so ownership is enforced in route and service code by filtering every query on `user_id` (`auth_guard.require_self`, `_validate_user`). The `db_user_scope` flag (off / shadow / enforce, `db/scope.py`) moves a request onto a user-scoped JWT so the policies apply; it is off by default (rollout: `docs/security/db-user-scope-rollout.md`).

## Data model

The schema is organized into eight bounded domains — Academics, Identity, Gradebook, Knowledge Graph, Study, Analytics, Ops, and Gradescope (migrations `0019`–`0028`). The central change is the catalog/offering/term split: an abstract `courses` catalog, per-term `course_offerings` (FK to `courses` + `terms`), and `terms`; the old `user_courses` table became `enrollments` keyed on `offering_id`. Different domains key on different levels of this split, bridged by `services/academics.py` (`current_term`, `resolve_offering`, `offering_course_id`): the knowledge graph stays on the **abstract `course_id`** so mastery is cumulative across terms, the gradebook keys on **`enrollment_id`**, and study artifacts + class analytics key on **`offering_id`**. The HTTP API boundary still speaks the abstract `course_id`; the resolver translates inward.

Identity is likewise split: `users` is slimmed to account state, with a 1:1 `user_profiles` table holding the encrypted name/profile fields; `services/profiles.py` provides decrypted display-name reads. The gradebook is enrollment-keyed (`gradebook_categories` with drop-lowest, enrollment-keyed `assignments`, plus curve policy on `enrollments`), and class analytics moved to `offering_concept_stats` / `offering_summary` (was `course_concept_stats` / `course_summary`). Knowledge-graph mastery history is now an append-only `node_mastery_events` table (replacing the old `graph_nodes.mastery_events` JSONB column), with UNIQUE-backed upserts for node/edge dedup. Ops tables (`feedback`, `issue_reports`) carry text/uuid PKs and FKs consistent with the rest of the schema.

## Background work

Three mechanisms, from lightest to heaviest:

- **FastAPI `BackgroundTasks`** for post-response work in one request: quiz submission's context update (`services/quiz/submission.py`) and, via `apply_graph_update(..., defer=background_tasks.add_task)`, its class-aggregate refresh (#847). The upload post-roll (`services/documents/post_roll.py`) runs as tracked asyncio tasks that the lifespan drains at shutdown.
- **The Postgres job queue** (#116, flag `jobs_queue`, default off): `services/jobs.py` over the `jobs` table's SQL functions (SKIP LOCKED claim, lease re-offer, backoff, dead letter), drained by `python -m worker` (its own Railway service, declared in `.railway/railway.ts` and not yet created on Railway). Handlers today: `course_context.refresh`, `document.process`, `document.index`, `gradescope.sync`. At-least-once, so every handler is re-runnable; payloads are ids only. `GET /api/admin/jobs` counts the queue with one `jobs_overview()` aggregate. With the flag on and no worker, aggregation and indexing only queue, while uploads and Gradescope syncs run inline after their pickup grace period.
- **The index sweeper** (`services/index_sweeper.py`), a lifespan task that re-drives unfinished RAG indexing (see the sharp edge below).

`services/course_context_service.py:474` `refresh_course_context` is the one trigger for an offering's class aggregates: flag off it runs `update_course_context` (`:219`) right there, flag on it enqueues a deduped job. The expensive LLM summary is hash-gated — it only re-runs when the stats hash changes — and it upserts into `offering_concept_stats` / `offering_summary`. `apply_graph_update` calls it for every touched course (inline unless the caller passes `defer=`), as do course add/delete. Achievement checks (`check_achievements`) are inline and wrapped in best-effort `try/except`.

## Multiple API replicas

Per-process state is being moved out so the API can run on two replicas (#117, `docs/deploy/railway.md` "Two API replicas", which audits every remaining piece of module-level state). Three global flags, all default off and turned on in this order: `stateless_rate_limit` (`services/request_limits.py` windows into `rate_limit_hits` + `claim_rate_limit()`), `stateless_locks` (`services/pg_lease.py` leases in `app_leases` for the study-guide single-flight, admin account operations and consumed OAuth nonces; the in-process lock stays as the first layer and a DB failure falls back to it), and `stateless_tutor_sessions` (lazily started tutor sessions and their end/delete tombstones in `tutor_pending_sessions`, materialised in one SQL transaction; once on it must stay on). The flag snapshot is already replica-safe through the `feature_flags_version` check. `API_REPLICAS` in `.railway/railway.ts` stays 1 until those flags are on.

## Feature flags

Flags are declared in code and configured in the DB (#620, ADR 0029):
`backend/services/feature_flags.py::REGISTRY` is the only place a flag's key,
variants and client-visibility are defined; its *configuration* — default
variant, percentage rollout, per-user/role rules — lives in
`feature_flags`/`feature_flag_targets` and is edited from `/admin`
(`routes/admin_flags.py`). Resolution is first-match-wins: a
`SAPLING_FLAG_<KEY>` env override, then fail-closed (unregistered flag,
invalid value, or an unreadable store), then a per-user rule, a per-role
rule, a stable percentage rollout, and finally the stored default —
anything that goes wrong resolves to `variants[0]` ("off"), never an
exception the caller has to handle. Backend code reads flags through
`flag_variant`/`flag_on`/`require_flag`; the frontend calls `useFlag(key)`
against the client-visible subset served at `GET /api/flags`. Reads are
served from a 30 s per-process snapshot cache that every admin write clears
on its own process; other processes notice within about 5 s under traffic,
because each re-reads the one-row `feature_flags_version` (bumped by triggers
on every flag write, `FEATURE_FLAGS_VERSION_CHECK_S`) and never later than the
TTL (`FEATURE_FLAGS_SNAPSHOT_TTL_S` / `FEATURE_FLAGS_ROLES_TTL_S` tune it, and
the E2E stack sets both to 0). The registry holds one `hide_<feature>` per
main-nav destination (all but Dashboard): `on` drops it from both nav skins
(`frontend/src/lib/navFeatures.ts`) and `NavFeatureGate` redirects its routes
to `/dashboard`; `off`, the fail-closed answer, leaves it visible. The rest
are rollout switches for the hardening work, analytics and the decision
seam: `decision_router`, `product_analytics`, `llm_fallback`, `llm_budget`,
`llm_outage_drill`, `jobs_queue`, `db_user_scope`, `realtime_rls`,
`async_db_client`, `stateless_rate_limit`, `stateless_locks` and
`stateless_tutor_sessions` (rollout order and kill switches in the
`docs/releases/2026-11-architecture-hardening*.md` release notes); of these, only `product_analytics` and `realtime_rls` are
client-visible. The admin API itself is the one place that does NOT fail closed on a
DB error — it raises, so a broken flag store shows up as an error rather
than a deceptively healthy "off".

## Known sharp edges

- `upload_document`'s worker agents run in parallel, but with `jobs_queue` off text extraction still runs before the stream opens by default (`OCR_ASYNC_ENABLED` moves it onto a thread inside the SSE context — ADR 0010's lightweight variant), so wall-clock ≈ extraction time + classifier + max(worker) time on the request path. With the flag on, that work runs on the worker instead.
- `apply_graph_update` (`backend/services/graph_service.py:1167`) takes a typed `services/graph_update_model.py::GraphUpdate` (a legacy dict is validated into it, exactly as leniently as before; malformed input now raises before any write). Callers pass different subsets: the upload persistence and concept scan (`services/documents/persistence.py`, `scan.py`) pass `{"new_nodes": [...]}` only, the tutor's agent tools (`agents/tools/graph.py`) register new concepts and mastery changes, and quiz scoring (`services/quiz/submission.py`) routes its mastery delta through it — appending a `node_mastery_events` row rather than writing `graph_nodes` directly.
- Agent failures no longer degrade to a second pipeline anywhere: a provider blip surfaces to the client as a retryable error (502 / terminal SSE / empty scan) rather than being papered over. The one deliberate second chance left is the streamed tutor's Rung-1 non-streaming fast-tier re-run, guarded so it never re-applies landed tool writes (ADR 0024).
- `apply_graph_update` imports `services.course_context_service` inside `_refresh_touched_course_contexts` (at module top it would drag the agents stack into every importer), outside its `try`: a broken import raises, while a failed context refresh is logged with `exc_info` and does not fail the caller. `graph_service.add_course`, `delete_node` and `delete_course` still swallow a failed refresh silently.
- With `jobs_queue` off, a caller that does not pass `defer=` (the tutor's graph tools, the upload paths) pays `update_course_context`'s aggregation for each touched course serially inside the request.
- Document-upload concept population only runs for `category in ("syllabus", "assignment")`; lecture notes, slides, readings, and study guides do NOT auto-populate the graph from upload — that path is the separate `/scan-concepts` endpoints (`backend/routes/documents.py:465`, `:515`; body in `services/documents/scan.py`).
- Sessions are lazy: `start_session` writes no `sessions` row; the row is materialized inside `services/tutor/pending.py::_consume_pending` on the first turn, so a session that's started and abandoned leaves no session history. Until then the pending greeting lives in `services/tutor_sessions.py`'s in-process store, or, with `stateless_tutor_sessions` on, in `tutor_pending_sessions` (expired by TTL). Turning that flag off after it was on strands the pending rows: their first turn answers 404.
- **RAG indexing is recoverable, but not by DBOS** (#482). `documents.index_status` (`pending` / `indexing` / `indexed` / `partial` / `failed` / `skipped`) is the indexing work queue. Both upload routes persist `extracted_text` at insert and hand the new id to `services/document_indexing.py::index_document` (through `schedule_document_index`, a `document.index` job when `jobs_queue` is on), which reads everything else off the stored row and owns every status transition; `services/index_sweeper.py` re-drives what did not finish, claiming batches through the `claim_documents_for_indexing` SQL function (`SKIP LOCKED`, attempts spent at claim time, bounded at 3). DBOS is deliberately not the mechanism: ADR 0011 keeps it off in every deployed environment, and the streaming route stays non-durable by design. Sharp edges that remain: the sweeper is off outside real model mode (so E2E never exercises a re-drive), a document from before #482 has no stored confidence and so re-indexes PRIVATE — including every row the derivation backfill marks `pending` — and an `indexed` document is never re-driven on its own. Re-sharing one is `scripts/backfill_document_chunks.py --doc <id>` or `POST /api/admin/documents/{id}/reindex`, which works only where a confidence was stored; a NULL-confidence row needs a fresh classification. A re-drive that cannot embed (function mode) leaves the row exactly as it found it; only a never-attempted upload records `skipped`. The sweeper claims one document per turn, so no lease runs down while a document waits, and a failed or partial document waits `lease_seconds` after its last attempt began before it is retried — on a finished row `index_leased_at` is that time, not a live lease. Stuck documents are listed at `GET /api/admin/documents/unindexed`.
