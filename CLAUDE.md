# Sapling

A FastAPI + Supabase backend that ingests student documents, calls Claude to classify/summarize/extract assignments, and serves a knowledge-graph-backed tutoring chat to a React frontend.

## Stack

- FastAPI: HTTP layer; app + router mounts in `backend/main.py`.
- Supabase (PostgREST): primary datastore; accessed via `httpx` REST through `db/connection.py`.
- Anthropic Claude (`anthropic`): the agents' LLM provider (ADR 0030), reached only through Pydantic AI agents. Haiku 5.5 on every generation slot, Sonnet 5.5 on the tutor and on `quiz_check` (the quiz's item checks, which must run on a model other than the Haiku quiz writer's, spec §13 A145); quality/cost is tuned with per-task `effort`. The one exception: the learning-loop slots (`check_items`, `grader`, `grader_second`, `learning_decision`, `loop_tutor*`, `session_close`) still default to Gemini until their eval datasets are re-recorded live against Claude — `agents/_providers.py::LOOP_SLOTS_PENDING_CLAUDE_EVAL`, pinned by `tests/test_anthropic_provider.py`; each already has its `_ANTHROPIC_EFFORT` level, so moving one is a default flip plus leaving that set.
- Gemini (`google-genai`): RAG embeddings only (`gemini-embedding-001`, 768-d — Anthropic has no embeddings API), the learning-loop slots awaiting their Claude eval pass (above), plus any slot an operator points back at a `gemini-*` model. The legacy `services/gemini_service.py` seam was deleted (ADR 0024).
- Pydantic AI: agent framework (`pydantic-ai-slim[google,anthropic]` in `requirements.txt`, pinned <2); agents live under `backend/agents/`.
- React frontend: lives in `frontend/` (out of scope for backend sessions).
- pytest: backend test runner, fixtures in `tests/conftest.py`.

## Conventions

- All Supabase access goes through `db/connection.py::table()`. Do not instantiate `httpx` clients or import `supabase` directly elsewhere. Two sanctioned exceptions: `db/migrate.py`, which connects with psycopg to run DDL, and `db/async_connection.py`, the async twin of `table()` (#117), which owns the per-event-loop `httpx.AsyncClient` for PostgREST behind the `a*` verbs on `table()`'s own handle (`await table("x").aselect(...)`) plus `arpc`/`apage_all` and asks `db/connection.py`'s `_scope_headers`/`_raise_for_status` on every request — async code reaches PostgREST through those, never through an `httpx.AsyncClient` of its own. (Third-party REST calls are not Supabase access: the OAuth userinfo fetch in `services/auth/signin.py` (the sign-in route's callback calls it), the PostHog person delete in `services/posthog_client.py::_delete_pass` and `services/typesafe_client.py`'s Jev client — see the LLM-calls rule below — use `httpx` directly; keep any new one that small and that obviously not Supabase.)
- Schema changes are append-only migrations in `backend/db/migrations/` (applied via `python -m db.migrate`); never edit an applied migration or run DDL in the Supabase dashboard. **New migrations use a UTC timestamp prefix** — `date -u +%Y%m%d%H%M%S` — because sequential `NNNN_` numbers are claimed at write time and only validated at merge, so concurrent branches collide. The 48 existing `NNNN_` files are frozen and must never be renamed: the ledger keys on basename, so a rename re-runs the migration. The count is 48 rather than 45 because three migrations applied out-of-band to staging had to be recovered under the exact basenames the live ledger recorded — the only reconciliation that clears an orphan without hand-editing a production ledger. That is the sole reason a new `NNNN_` file is ever sanctioned; anything genuinely new uses a timestamp. Full rationale in `backend/db/migrations/README.md`.
- Term/offering/enrollment resolution goes through `services/academics.py`. The HTTP boundary keeps the abstract `course_id`; the graph stays on the abstract course, gradebook keys on `enrollment_id`, and study/analytics key on `offering_id`.
- Display names are resolved via `services/profiles.py` (`get_display_name`/`get_display_names`), which decrypts off `user_profiles` — don't read name columns off `users`.
- All LLM calls are Pydantic AI agents in `backend/agents/` (model slots in `agents/_providers.py`); there is no other sanctioned LLM seam (ADR 0024). There is no raw `anthropic` client anywhere — Claude is reached only through pydantic-ai's `AnthropicModel` inside `_providers.py` (token counting included: `scripts/bench_quiz_prompt_budget.py` calls `model_for("quiz").count_tokens`). Exactly three raw `google.genai.Client` sites remain: `services/rag_service.py`'s embedding client (request-path, lazy, `model_mode()`-gated per #439), `scripts/_raw_gemini.py` (offline benchmark baseline — its docstring forbids importing it from application code), and `scripts/ingest_catalog.py` (offline ops CLI, lazy but deliberately ungated: catalog ingestion is meaningless without real embeddings — see the comment there). The two script sites are outside the request path and are never imported by application code. The one sanctioned non-Pydantic-AI model client is `services/typesafe_client.py` (TypeSafe's Jev over `httpx`): Jev is a typed decision model, not a text LLM (ADR 0027), and it is reached ONLY through `services/decisions.py`, which gates it on `model_mode()` and degrades to the `decision` agent.
- **RAG rows carry a `visibility`, and every retrieval names its reader.** Indexing resolves the uploader's STORED `user_settings.share_class_context` through `services/chunk_visibility.py::visibility_for` (#629) — never the per-request `use_shared_context` body flag, which is a read-side hint the tutor never sets. An opted-out upload is hashed into a per-uploader private id namespace (`rag_service.chunk_id`), because the shared upsert merges `on_conflict=id` and a colliding id would leave that student's text in the class pool under a row they can no longer withdraw. `retrieve_chunks*` take `user_id`; omitting it asks for shared rows only, so a caller that has not been threaded through under-retrieves rather than leaking. Shared rows are jointly owned — `course_chunk_contributors` is what makes "withdraw my chunks" answerable, since `uploader_id` names only the last writer of a deduped row.
- **A chunk is shared only when the document is the course's to share AND its uploader consents.** `chunk_visibility.decide_visibility` composes both (#630 on top of #629): only `shareability='course_material'` above `MIN_SHARE_CONFIDENCE` can be shared, `completed_work` is always private (serving a classmate a student's own answers is an academic-integrity failure, not just a privacy one), `personal_notes` is private by default, and every unknown answer — a `shareability` the model omitted, a value outside the enum, a missing confidence — resolves to private. The decision is stored on `documents.shareability` so a re-index or backfill can reproduce it instead of privatising everything. `index_document_chunks` takes `visibility=` AND `category=` as required keyword-only args; `category='catalog'` is refused (that value is the BU-catalog partition two readers key on).
- Knowledge-graph mutations go through `services/graph_service.py::apply_graph_update` — routes never write `graph_nodes`/`graph_edges` directly.
- **An agent read tool that can return zero rows routes that result through `services/tool_signals.py::report_empty_result`.** Three personalization inputs were silently empty for months (#529's swallowed 42P10, the misconceptions `offering_id`/course-id keyspace mismatch, the digest key drift) because an empty list is indistinguishable from "this student has nothing yet". The helper supplies the missing half — whether the student *plausibly should* have data — and emits `quiz.tool_empty` when the two disagree. It is feature-agnostic (`feature=` names the caller), so tutor tools use it too.
- `functools.lru_cache` is reserved for **deterministic, per-process reads** (#98) — either immutable mappings that never need invalidation (e.g. `academics.offering_course_id`) or reads with a matching `clear_*_cache()` hook that every mutator calls (e.g. `course_context_service.get_course_context` is cleared by `update_course_context`; it is a small per-entry TTL cache rather than an lru_cache so other workers converge within its TTL, #771). Cache only hashable-arg functions; return a deep copy if the cached value is mutable; never cache without a clear invalidation story. The autouse `_clear_lru_caches` fixture in `tests/conftest.py` resets these between tests.
- Backend tests live in `backend/tests/` and run via `pytest`; shared fixtures (mock Supabase, mock Gemini) are in `tests/conftest.py`.
- Routers are mounted in `main.py` with `/api/<name>` prefixes; new routes follow that pattern.
- **Routes stay thin; two CI gates hold it** (#118). No route file over 600 lines and no function over McCabe complexity 25: `backend/code_size_baseline.json` is EMPTY (its last ceiling, `routes/learn_loop.py`, went with that route's split into `services/loop/`), so any new offender fails `tests/test_code_size_ratchet.py` — move the logic into its `services/<domain>/` package rather than hand-raising a ceiling. Import boundaries live in `backend/.importlinter` (`lint-imports`): `routes | worker` over `services : agents : models` over `db`, and a domain package is reached from another only through its `__init__`. A new exception goes in `ignore_imports` with its reason; a stale one fails the run.
- **Gate unfinished or risky features with a flag** (`flag_on(key, user_id)` / `require_flag(key)` on the backend, `useFlag(key)` on the frontend). Declare the flag in `services/feature_flags.py::REGISTRY` (variants[0] must be `"off"`); never gate with a new env var or a per-feature `user_settings` column.
- **Verify substantive changes against the E2E lanes before merge**: hermetic suite + the Chapter 1 Playwright lane + the oracles (all three where applicable — `e2e.yml` re-runs the lane on every push to main, but pre-merge is the gate that can still say no). A bug fix in E2E-covered territory pairs with a promoted regression journey in `frontend/e2e/` (triage/promotion recipe: `docs/e2e-exploration.md` §7–§8; journey style: fixtures-based `test` from `support/fixtures.ts`, DB asserts via `support/db.ts`, testids per `docs/frontend-testids.md` "Adding a surface").
- **E2E runs in numbered slots; :3000/:5000 are the dev app's.** Every local E2E stack boots in a slot (`scripts/lib/e2e-slot.sh`): slot N (1..3) = frontend :310N, backend :510N, its own Supabase project `sapling-e2e-N` on ports +100·N, a throwaway DB. Run whole cycles through `scripts/e2e-cycle.sh` (or `make e2e`), which claims the first free slot's lock (`/tmp/claude-<uid>/sapling-e2e-slot-N.lock`) for up→test→down — concurrent runs (yours, subagents', other sessions') take other slots instead of queueing. Never boot E2E on :3000/:5000/:54321: those are the human dev stack, and Google sign-in can only land on :5000. Slot 0 is that classic stack and is refused outside CI (`e2e.yml`, main-only for cost — a PR runs the lane locally in a slot before merge). `make explore`, `make gallery-shots` and `scripts/figma-capture.sh` claim slots the same way. `make e2e-up`/`e2e-down` start and stop a cycle held in the background; `scripts/e2e-up.sh`/`e2e-down.sh` refuse to run outside a cycle. One cycle per checkout — parallel runs come from separate worktrees. A human views a slot at `http://127.0.0.1:310N` (cookies ignore ports, so `localhost:310N` would overwrite the dev app's sign-in).
- **Student surfaces stay WCAG 2.1 AA (learning-loop spec §13 A135).** `frontend/e2e/a11y.spec.ts` runs axe-core (`e2e/support/a11y.ts`: wcag2a/2aa/21a/21aa, nothing excluded) over every student surface in its key states and fails on any violation — a new student surface or state adds its scan there; `e2e/learn-keyboard.spec.ts` walks the loop with the keyboard alone. Text colour comes from the `globals.css` tokens, each AA on every surface it meets (never an opacity dim on text). A control that its own action disables or removes must hand focus on, and new content (a question, a result) takes focus or lands in a live region that was on the page before it (see LoopLearn's `focusAfter`).
- **Structured-output bounds are local on Claude.** Claude's strict JSON mode cannot enforce `maxLength`/`minimum`/`maximum` at decode time (pydantic-ai moves them into the field description), so an overshoot fails Pydantic validation and burns output retries. Free-prose length caps use `agents/_bounded.py::clip_prose` (word-boundary clip, logged); list caps use the `_clip` before-validator pattern (`agents/quiz.py`); an ordering the callers rely on is imposed in a validator (`ConceptList._order_by_importance`), never trusted to the model.
- **Function-mode seam**: the E2E lanes run `SAPLING_MODEL_MODE=function` with fixed handler constants from `agents/function_handlers_e2e.py` (the seam serves STREAMED runs too since #349 — the SSE tutor replays the same constants) — every upload "summarizing" gradient descent is the seam working as designed, not a data bug (the tell: byte-match to an `E2E_*` constant). New request-path agent tasks need a handler registered there (unregistered tasks raise `UnregisteredHandlerError`); post-response BackgroundTask handlers stay deliberately unregistered. Keep handler constants ↔ spec assertions ↔ `tests/test_e2e_function_handlers.py` in sync. Code below the `agents/_providers.py` seam must never construct a raw `google.genai.Client` without a `model_mode()` gate (#439). The mode is frozen at boot (#771): the lifespan calls `freeze_model_mode()` first, so agents (built at import) and every `model_mode()` gate agree for the life of the process; before the freeze (unit lane, scripts) it is read per call.

Never make the repo public, or copy those files anywhere public, without first moving them out (e.g. a private repo fetched at build time).
- Column-level encryption is on for sensitive columns: `user_profiles.name`/`first_name`/`last_name`/`bio`/`location` (these moved off `users` to `user_profiles` in the 0024 identity split), Google OAuth tokens, `messages.content`, `room_messages.text`, `sessions.summary_json`, `documents.summary` + `concept_notes` + `extracted_text` (the RAG OCR text added in 0030), `notes.title`/`body`/`last_summary`, `assignments.notes`/`points_possible`/`points_earned` (the enrollment-keyed gradebook table; points columns carry numeric semantics — use `decrypt_numeric` at read), `feedback.comment`/`topic` + `issue_reports.topic`/`description` (free-text user input, #520), `quiz_attempts.questions_json`/`answers_json` + `quiz_context.context_json` (quiz performance data, #521; scalar analytics columns — score/total/difficulty/completed_at — stay plaintext) + `quiz_responses.answer_text` (written quiz answers via `encrypt_json`; the rest of `quiz_responses` stays plaintext scalars) + `topic_checklists.content` (the material-derived topic outline), `document_uploads.file_data`/`result` (#116 queued uploads; `file_data` via `encrypt_bytes`, cleared at a terminal stage), `course_chunks.chunk_text` (the RAG chunk store, ADR 0025/#484 — UNIFORM across document AND catalog rows so the `ciphertext` oracle can assert one invariant; ids are content hashes over the PLAINTEXT and encryption happens AFTER embedding, or the vectors are noise), and `flashcards.front`/`back` + `study_guides.content` + `room_summaries.summary` (derived content, #518; `study_guides.content` uses the JSON pair, `room_summaries.summary` keys its cache on the separate plaintext `member_hash` column so encryption doesn't affect cache-hit lookups). Learning-loop check items (PKG-04): `check_items.prompt`/`reference_answer`/`final_answer`/`rubric_json`/`common_wrong_json`/`options_json`/`correct_option`/`canonical_answer`/`surface_context` (course assets; `rubric_json`/`common_wrong_json`/`options_json` hold JSON, `question_hash` is the plaintext lookup key hashed from the plaintext prompt; A140's `surface_context` names an item's scenario, while `surface_representation` is a plaintext enum and A141's `apex_key`/`component_keys` are plaintext concept keys). Learning-loop sessions (PKG-09): `sessions.close_json` (the session close, the JSON pair) and `sessions.loop_brief` (the learner brief, built once per session; an empty brief is still a ciphertext, so NULL means "not built yet"). `sessions.loop_state` is PLAINTEXT jsonb (ids, numbers, booleans, enums), but two values inside it are ciphertext: `goal.text_encrypted` (the student's goal text, ADR 0033) and a step's or `probe.current`'s `grade_checkpoint` (the sealed saved grade, ADR 0038). Learning-loop misconceptions (PKG-10): `misconceptions.evidence_text` (the student's answer a misconception was recorded from; `wrong_key` is the plaintext lookup key). Learning-loop teach prompts (A138, A139): `learning_prequestions.guess_json` (a prequestion guess, the JSON pair; NULL exactly for "no idea") and `learning_self_explanations.reply_text` (a self-explanation reply; its length `reply_chars` stays plaintext for the admin report). Helpers live in `backend/services/encryption.py`; use `encrypt_if_present` at write boundaries and `decrypt_if_present` / `decrypt_numeric` at read boundaries (including before injecting into AI prompts). `ENCRYPTION_KEY` must be set (32 bytes as 64 hex chars; generate via `python -c "import secrets; print(secrets.token_hex(32))"`). Deliberate exception: `newsletter_emails.email` stays plaintext (ADR 0026; its `first_name`, set only by a /pending waitlist join, IS encrypted) — the UNIQUE constraint, lookup index, and both subscribe/allowlist upserts key on the value, and AES-GCM's per-call nonce breaks value equality.
- **A backend boots only with the ENCRYPTION_KEY its database was written under.** `services/encryption_canary.py::verify_encryption_key` runs in the lifespan before any resource starts (after `freeze_model_mode`, `validate_config` and `check_slot_guards`, none of which reads or writes an encrypted column): it opens the one-row `encryption_key_check` canary (seeded by the first boot) and raises on a mismatch, because the read helpers fail SOFT — a laptop pointed at prod's SUPABASE_URL with its own key otherwise re-encrypts rows prod can never read (2026-10-21). A missing table/unreachable DB only warns. Rotating the key = re-encrypt every 🔒 column, then delete that row.
- **Learning-loop tables are service-only** (#115 bucket E, spec §13 A148): RLS on, no policy, nothing for anon/authenticated (`20261109032302_learning_loop_rls.sql` restates it last, so production's order — main's RLS migrations first — ends the same). The loop router and a `/api/learn` request the loop gate delegates (`_loop_delegate`) run as service; a loop store a user-scoped route reaches is `@runs_as_service`, listed in `tests/test_service_scope_allowlist.py` (which scans `learning/` too). A new loop table gets the same posture in its own migration; `tests/integration/test_rls_lockdown_db.py` pins it (and `SERVICE_ROLE_NARROWED`, the append-only records whose service_role grant stays narrow).
- Knowledge-graph mastery is now an append-only `node_mastery_events` table (replaced the `graph_nodes.mastery_events` JSON column in 0023); node/edge dedup is enforced by UNIQUE constraints. Don't read/write a `mastery_events` column. A row is never edited or deleted to retract it: evidence graded against a staff-retired check item is VOIDED by an append-only `learning_evidence_voids` row (learning-loop spec §13 A123) and the state recomputed from the non-void journal — a new evidence reader must leave void rows out (`learning/void_store.py`).
- **Floats through PostgREST are exact** (spec §13 A136): the Supabase image's `postgresql.conf` sets `extra_float_digits = 0` (float8 → 15 significant digits, real → 6, in text and `to_jsonb`), so `20261108162223_learning_exact_floats.sql` sets it to 3 on `service_role`, which PostgREST applies to every backend request, and `20261109032302_learning_loop_rls.sql` (A148) on `authenticated`, the role a `db_user_scope` request reads as. Any other role PostgREST runs the backend as needs the same; a psycopg connection still gets the server default, so read exact values there with `binary=True` (as `tests/integration/test_exact_floats_db.py` does). The fence: `scripts/learning_release_verify.py --rest-float-probe`.
- The eval harness (`tests/evals`) never touches a database in any mode: the AI budget reads an empty in-memory store (`_replay.hermetic_budget`) and a run's usage is captured, never enqueued (`_replay.usage_log`; `SAPLING_EVAL_USAGE_LOG=<path>` writes it, so a re-record measures tokens).
- Optional cross-worker cache (#97): `services/cache.py` wraps Redis and is **off by default** — with no `REDIS_URL` set it's a zero-overhead no-op and never fails a request (any Redis error → clean miss + warning). Currently backs the content-addressed OCR/extraction cache (`extraction_service.extract_text_from_file`, keyed on `sha256(file_bytes)` + engine). The `redis` dependency is only imported when `REDIS_URL` is set.
- PostHog (ADR 0028) runs ALONGSIDE `events_service`, not instead of it — admin analytics stay on our tables, and events reach PostHog only via the mirror in `log_event` (never a `posthog.capture` in a route; a new event goes into `EVENT_TAXONOMY`). LLM analytics are the `$ai_generation` mirror of each `llm_usage` row (model/provider/tokens/cost/trace id — never content); there is NO OTel span export to PostHog and no `Agent.iter` patch, so an agent run is covered exactly when it reports through `record_agent_usage`. It is forced OFF — no client, no queue, no network — under pytest, `APP_ENV=test`, any non-`real` `SAPLING_MODEL_MODE` (read via `agents._providers.model_mode()`), or an unset `POSTHOG_PROJECT_TOKEN`; that gate is decided ONCE, when `initialize_posthog` builds (or declines) the client. The runtime switch is the `product_analytics` feature flag, read on the worker per student (bounded, failures cached briefly) — `POSTHOG_DISABLED` is deprecated (a truthy leftover still keeps the client unbuilt, with a WARNING). The local E2E/explore stacks do not rely on function mode for this (a cycle defaults to it, but `SAPLING_MODEL_MODE=real` is allowed, and they run `APP_ENV=local`): `scripts/e2e-up.sh` and `scripts/explore.sh` blank `POSTHOG_PROJECT_TOKEN` explicitly. **Every PostHog event is attributed to a consenting student, or not sent** — no personless events, so work with no actor (sweeper, DBOS, the pipeline outside a request) never reaches PostHog. The request path only ENQUEUES via one `_submit` (no gate re-read, no I/O — an exception is queued as a plain frame summary and its `$exception_list` is built on the worker; drops DNT/GPC requests and `error.4xx`; templates `path`/`route`; strips foreign user ids; actor = the item's user id, and ONLY when that is `None` the session user `request.state.user_id` — a placeholder or malformed id is dropped, never re-attributed); consent (`analytics_consent.consent_for`: opt-out `user_settings.analytics_opt_out`, soft-deleted, unknown or unreadable → drop) runs ONLY on the worker, so no event-loop thread reads the DB. DNT/GPC is honoured per request only: work outside a request (sweeper, DBOS) follows the stored opt-out alone — deliberately, a browser signal is not persisted as a choice. Account-deletion erasure is NOT gated by the flag or the token (it runs whenever the personal key + project id + API host are set), so a lane that must stay silent blanks `POSTHOG_PERSONAL_API_KEY` too, as `scripts/e2e-up.sh` / `scripts/explore.sh` do. Its per-process TTL cache is invalidated by the settings PATCH and account deletion — a new mutator of either must call `clear_analytics_consent_cache`. `users.id` is opaque TEXT (`user_<google id>`), not a UUID: never gate on a UUID regex.
- HTTP caching (#99): conditional GETs use `services/http_cache.py` (`make_etag`/`conditional`/`cached_json`). `Cache-Control` on these routes is **always `private`, never `public`** — the responses carry user-scoped, app-decrypted columns that must never be cached at a shared proxy/CDN. Derive the ETag from cheap change-keys (ids, `updated_at`, existing content hashes), not from the fully-built payload.
